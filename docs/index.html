The ALAC Pipeline

Apple Music delivers lossless audio via HTTP Live Streaming (HLS). Audio is encoded in ALAC (Apple Lossless Audio Codec) at up to 24-bit/192kHz and packaged inside fragmented MP4 containers (ISO Base Media File Format). aria's pipeline has six stages, each solving a distinct engineering challenge.

1

Metadata & HLS Resolution

Every track is identified by an adamId — a numeric catalog identifier (e.g. 1850496033). The pipeline begins by resolving this to streaming metadata via Apple's amp-api.music.apple.com REST API.

A GET /v1/catalog/{storefront}/songs/{id} request returns: title, artist, album, artwork URLs, duration, ISRC, composer credits, and audio traits (lossless, spatial, Atmos).

The storefront parameter controls regional availability. A track may exist in us but not cn — particularly relevant for new releases where disc 2 tracks may appear in one region days before another.

To obtain the HLS master playlist URL, aria sends a WebPlayback request to play.itunes.apple.com, returning streaming assets categorized by flavor — codecs like 28:ctrp256 (AAC 256k) and ALAC variants.

Variant Selection

The HLS master playlist lists multiple audio variants. aria's m3u8_select.py parses this and selects the best ALAC variant.

The selection picks the highest sample rate ALAC up to max_sample_rate_hz (default 192kHz). The variant also carries key URIs — SKD URLs identifying which key contexts apply to which segments, extracted via regex matching skd://itunes.apple.com/....

AlacVariant(
    sample_rate_hz=48000, bit_depth=24,
    average_bandwidth=1536000,
    stream_url="https://aod-ssl.itunes.apple.com/.../_m.mp4",
    keys=["skd://.../P000000000/s1/e1",   # prefetch context
          "skd://.../p1443135819/c6"]      # content key
)
3

Fragmented MP4 Parsing

The selected variant's stream_url points to a single fragmented MP4 (fMP4) containing the entire track. Unlike regular MP4 where all metadata is in moov, fMP4 splits audio into fragments — each with its own moof/mdat pair.

ISO BMFF Box Structure

An MP4 is a tree of boxes (atoms). Each box: 4-byte size + 4-byte type + payload. aria's m4s_parser.py walks this tree to locate every audio sample.

┌─ ftyp ─────────────────────────────────────────────────────────────┐
│  File type: iso5, isom, hlsf                                       │
└────────────────────────────────────────────────────────────────────-┘
┌─ moov ─────────────────────────────────────────────────────────────┐
│  └─ trak → mdia → minf → stbl                                     │
│     └─ stsd (sample descriptions)                                  │
│        ├─ enca [1] ── sinf (protection) + alac (codec config)       │
│        └─ enca [2] ── sinf (protection) + alac (codec config)       │
└────────────────────────────────────────────────────────────────────-┘
┌─ moof (fragment 1) ── tfhd: desc_index=1 ────────────────────────┐
│  └─ traf                                                           │
│     ├─ trun  sample_count=175, sizes[], durations[]                │
│     ├─ senc  sample encryption IVs + subsample ranges              │
│     ├─ saiz  auxiliary info sizes per sample                       │
│     └─ saio  auxiliary info offsets                                 │
├─ mdat ─── [sample bytes × 175] ───────────────────────────────────┤
└────────────────────────────────────────────────────────────────────-┘
┌─ moof (fragment 2) ── tfhd: desc_index=2 ────────────────────────┐
│  └─ traf  (trun: 165 samples + senc/saiz/saio)                    │
├─ mdat ─── [sample bytes × 165] ───────────────────────────────────┤
└────────────────────────────────────────────────────────────────────-┘
  ... fragments 3–16 (desc_index=2)

Sample Extraction

Each trun (Track Run) contains per-sample size/duration entries. The parser walks mdat payloads using these sizes:

offset = mdat_payload_start
for entry in trun.entries:
    sample_data = buf[offset : offset + entry.size]
    samples.append(Sample(data=sample_data, desc_index=tfhd.desc_index))
    offset += entry.size

The desc_index (from tfhd) tells which key context applies. Fragment 1 uses index 1; fragments 2–16 use index 2.

A typical 4-minute ALAC track at 48kHz/24-bit: ~2,650 samples across 16 fragments, ~48 MB total. Each sample ≈ 18 KB — one ALAC frame of 4,096 PCM samples.
4

Sample-by-Sample Processing

Extracted samples are processed through a localhost TCP service using a pipelined dual-thread architecture.

Writer thread                    Processing service (:47010)             Reader thread
─────────────                    ───────────────────────────             ─────────────
     │                                      │                                │
     │── key context header ───────────────►│                                │
     │   (adamId + key URI)                 │◄── establish context           │
     │                                      │                                │
     │── [uint32 len][sample 0] ──────────►│                                │
     │── [uint32 len][sample 1] ──────────►│── process ──►[result 0] ──────►│
     │── [uint32 len][sample 2] ──────────►│── process ──►[result 1] ──────►│
     │── ...                                │── process ──►[result 2] ──────►│
     │                                      │                                │
     │── [0x00000000] (end context) ──────►│                                │
     │── new key context ─────────────────►│                                │
     │── [samples for context 2] ─────────►│── process ──►[results] ───────►│

Concurrency Control

Writer and reader run in separate threads, gated by a semaphore(64). Writer acquires before each send; reader releases after each read. This backpressure prevents TCP buffer flooding when processing is slower than the network.

Key Context Switching

When desc_index changes between fragments, the writer sends 0x00000000 then a new key context header. A typical track has 2 contexts: init/prefetch and content.

Throughput: ~12 MB/s on loopback — a 48 MB track in ~4 seconds.

5

M4A Container Repair

After processing, we have the original fMP4 plus processed sample data (same lengths). m4a_writer.py does an in-place structural patch.

The Problem: Only First Fragment Played

Initial implementation: 50 MB file but only 14.9 seconds of audio decoded (175/2,650 samples). The remaining 93% was silent.

Root Cause 1: Incomplete stsd Patching

stsd had two enca entries. Code renamed the first to alac and removed its sinf, then breaked — leaving entry #2 untouched. Fragment 1 used desc_index=1 (patched, worked). Fragments 2–16 used desc_index=2 (still enca, demuxer refused).

Root Cause 2: Residual Encryption Metadata

Each traf had senc/saiz/saio boxes telling demuxers samples were still protected — even after renaming enca→alac.

The Fix

A) Iterate ALL enca entries in stsd: rename type to alac, remove sinf, adjust ancestor sizes.

B) Walk every traf: overwrite senc/saiz/saio type fields with free (standard ISO BMFF padding box). Same size = preserves all byte offsets.

for traf in find_all_trafs(buf):
    for box_type in [b'senc', b'saiz', b'saio']:
        for box in find_boxes(traf, box_type):
            buf[box.offset+4 : box.offset+8] = b'free'
Why ffmpeg remux loses data on fragmented ALAC

ffmpeg -c copy -movflags +faststart reads the moov duration, which in fMP4 only describes the first segment (~15s). The remuxed output drops all subsequent fragments. The in-place patch avoids this by preserving the original fragment structure.

Multi-Instance Architecture

DecryptPool: Round-Robin + Per-Instance Mutex

class DecryptPool:
    def __init__(self, instances=4):
        self._instance_locks = [threading.Lock() for _ in range(instances)]
        self._round_robin = 0

    def process_track(self, samples, keys, track_id):
        idx = self._round_robin
        self._round_robin = (idx + 1) % self._instances
        with self._instance_locks[idx]:  # one track per instance
            return self._process(idx, samples, keys, track_id)

Why Not Persistent Connections?

An earlier design reused TCP connections across tracks. After 2–3 tracks, session state accumulated and corrupted, crashing the service. Fix: fresh TCP connection per track. Overhead: ~1ms connect vs 4s processing.
